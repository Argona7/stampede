## 2. Маскот — самостоятельный дизайн-этап через Higgsfield

### Выбранное направление

**Тяжёлый компактный бизон в движении.** STAMPEDE — движение стада, масса, направленность; силуэт бизона связывает имя с образом без буквального графика цены. Характер: собранный, упрямый, энергичный; не плюшевый ребёнок и не злой демон.

Визуальная подпись: массивная передняя часть, узнаваемый горб, короткие рога с оригинальным изгибом, низкий центр тяжести, одна широкая красная фронтальная плоскость. Чёрный корпус не исчезает на чёрном: форму отделяет нейтральный контур/матовый серый свет. Красный не превращается в розовый неон.

Это арт-направление, а не готовый рисунок. Fable должен спроектировать узнаваемую форму, а не просить генератор «cool crypto bull».

### Три концепта перед финальным выбором

Создай через Higgsfield **три отдельных изображения**, не коллаж из вариантов:

1. **Monolith:** лаконичный, почти графический бизон — несколько крупных плоскостей, минимум деталей, сильный контур. Приоритетный кандидат для аватара.
2. **Stamp:** более угловатая эмблема того же животного, словно плотный печатный знак. Проверить, не разваливается ли образ в маленьком размере.
3. **Motion:** слегка объёмный матовый персонаж в низкой беговой стойке; выглядит как дорогой коллекционный дизайн-объект, не как типовой игровой монстр.

Во всех трёх — чёрный/красный/нейтральный свет, без текста и окружения. Покажи владельцу одновременно, укажи свой выбор и две причины. **До выбора владельца не делать дорогую серию поз и анимаций.** После выбора зафиксировать изображение как reference/master; дальнейшие генерации делать с ним, а не каждый раз из текста.

### Что исключить

Без монет, долларовых знаков, ракет, свечей, короны, худи, очков, оружия, огня, золотых рогов и робота с LED-лицом. Не переносить чужой маскот. Не делать бренд «красный бык на фоне растущего графика». Брендовая энергия — от силуэта и движения, не от обещания роста цены.

### Мастер-набор после выбора

- Master: чистый персонаж 2048×2048 или больше; сохранить исходный результат генерации и идентификатор задания/модели.
- Прозрачный PNG с настоящим alpha, а не нарисованной шахматной сеткой; варианты на чёрном и светлом фоне.
- Аватар: крупная голова/передняя часть, читается в круглом кропе; варианты 1024×1024 и 128×128.
- Статичная hero-поза: три четверти, движение к центру композиции. Миниатюрный знак для README/favicon: упрощённая форма, проверка на 32 и 64 px.
- Одна короткая анимация: 3–4 секунды, наклон вперёд/тяжёлый шаг/возврат в исходную позу. Зацикливание без скачка, морфинга рогов, лишних ног и смены лица. ASCII-версия — упрощённый вручную проверенный знак для терминала, не ANSI-картинка на сотни колонок.

Не называть PNG «вектором». Если нужен SVG, создать реальные векторные контуры и проверить, а не положить PNG внутрь SVG и выдать это за векторный мастер. Слово STAMPEDE и весь интерфейсный текст набирать отдельно; генератор не должен рисовать буквы для финального логотипа.

## 3. Визуальная система README

### Палитра и типографика

`#050505` — чёрный; `#0D0A0A` — панели; `#FF3344` — основной красный; `#351419` — тёмный разделитель; `#F2F2F2` — основной текст; `#A3A3A3` — вторичный текст. Сохранить связь с работающим приложением. Маскот не приносит новые акцентные цвета.

Графические заголовки и wordmark — выразительная типографика из текущего проекта, рабочие подписи — IBM Plex Mono. Основной текст Markdown остаётся нативным шрифтом GitHub. Не превращать всю документацию в картинки ради кастомного шрифта.

### Ограничения GitHub — учитывать с первого макета

README не исполняет пользовательский JavaScript; GitHub удаляет script, inline styles и ряд HTML-атрибутов. Поэтому не проектировать GSAP, canvas или произвольный CSS как часть README. Нельзя гарантировать чёрный фон всей страницы в светлой теме GitHub.

Рабочая конструкция: чёрные брендовые изображения/анимированный GIF + обычный читаемый Markdown + допустимые HTML-элементы. SVG использовать для статичной графики; анимацию SVG не считать надёжной основой. Анимированные блоки делать GIF, полное MP4 открывать по кликабельному poster/link. Сворачиваемые детали — нативный `<details>`.

Официальные источники: https://github.com/github/markup#github-markup ; https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/organizing-information-with-collapsed-sections . Проверить результат в реальном GitHub-renderer, не только в VS Code preview.

### Первый экран: макет сверху вниз

**HERO, 1280×480 исходник.** Слева STAMPEDE крупно, справа маскот, между ними много свободного места и один направленный красный штрих. Не наваливать поверх него карту, логи, бейджи и ещё пять слоганов. В hero достаточно имени и персонажа; смысл продукта написан живым текстом сразу ниже.

**Одна фраза:** `See what wallets sold before they bought the next coin.` Следом точное пояснение: read-only explorer of observed wallet rotations on supported Robinhood Chain venues. Не называть это доказанным переносом денег.

**Навигация:** `Quickstart · Watch demo · How it works · Data & limits`. Реальные якоря/ссылки. Не более трёх честных badges, только при существующей лицензии/CI/release; никаких пустых GitHub Stars, fake build passing и лишних vendor badges.

**Quickstart должен находиться в пределах первых двух desktop-экранов.** Пользователь не прокручивает галерею на три метра, чтобы найти запуск.

### Анимация — два акцента, не аттракцион

1. Hero-loop: маскот делает один тяжёлый шаг/наклон, красная линия коротко подчёркивает wordmark, затем 1–2 секунды спокойного удержания. Само слово не дёргается и не распадается по буквам. 3–4 секунды; визуально чистый первый кадр и шов цикла. Можно собрать типографику/линию детерминированно поверх принятой анимации маскота.
2. Product-loop: 6–8 секунд выбранного маршрута/перехода к evidence из настоящего продукта. Не ускорять счётчики сверх обозначенного replay и не подменять данные декоративными цифрами.

Оба loop не должны одновременно агрессивно мигать. Для каждого есть статичная версия и понятный alt text. Цели веса: hero GIF до 3 MB, product GIF до 5 MB, все видимые медиа README суммарно до 10 MB. Если оптимизация портит текст, уменьшить длительность/частоту кадров, а не превращать шрифт в артефакты. Это проектные бюджеты, не заявленные лимиты GitHub.

## 4. Содержание README после hero

Организовать пять коротких смысловых блоков; подробности увести в docs:

1. **Run the demo.** Записанная небольшая выборка, запуск без Alchemy/Twitter/Higgsfield ключей. Проверенные команды, ожидаемый адрес web, команда TUI, размер скачивания и требования. Live-путь с ключами отдельно. Не писать «one command», пока она реально не существует.
2. **Four views, one dataset.** TERMINAL — поток наблюдений; RADAR — ранжирование по описанным признакам; FLOW — источники и назначения для монеты; MAP — пространственный обзор. Один общий визуальный strip или максимум две компактные картинки, не четыре огромных повторяющихся GIF.
3. **From an event to evidence.** Один реальный пример из принятой выборки: wallet → sell transaction → buy transaction → observed sequence. Указаны окно, время и роль distinct wallets vs sequence rows. Ссылки проверяются. Маскот не заменяет evidence.
4. **What it does / what it does not.** Read-only; replay/live отделены; поддержанные площадки; атрибуция адреса не равна личности; radar score не является доказанной доходностью. Исследовательские lift-числа из пятичасовой выборки не выносить в hero как обещание заработка.
5. **Development.** Компактная схема потока данных, реальные команды tests/build, docs, contributing, известные ограничения, короткий roadmap из трёх конкретных задач. Отмечать planned отдельно от shipped. Лицензия выбирается владельцем с учётом зависимостей.

Критерий качества текста: читатель за 20 секунд понимает, что это, что видно в демо и куда нажать для запуска. README должен приносить пользу даже при отключённых картинках.
